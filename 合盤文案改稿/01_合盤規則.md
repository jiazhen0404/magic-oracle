# 合盤規則

一份合盤不是二十四段各自正確的文字，是**一個必須整體成立的判讀**。

這份規則全部來自實際踩到的問題——每一條後面都附了發生率與實例。不是理論。

**最高層的要求只有一句：全文不得上下文矛盾。** 底下十六條是把這句話拆成可以檢查的條件。

---

## 一、軸的分工

系統有九個判讀軸，各自回答一個問題。**越界是矛盾最主要的來源。**

| 軸 | 只能回答 |
|---|---|
| 分數帶 | 這段緣有多深、多有份量 |
| 節奏 | 你們是怎麼開始的 |
| 相遇 | 在什麼場合遇上、多久才顯現 |
| 主動方 | 誰先動心、誰先出手 |
| 機會 | 走到一起的機會多大、卡在哪 |
| 格局 | 順不順、位置對不對等 |
| 夫妻宮 | 各自期待什麼樣的相處 |
| 下一步 | 接下來該由誰先開口 |
| 三維度 | 溫度／重量／長度各自的狀況 |

### 規則 1　一個軸不得替另一個軸下斷言

**為什麼**：免費頁上各軸並列顯示，越界會在相鄰兩段當場矛盾。

**實例**：分數帶「緣暖」原本寫「你們不是一見面就燒起來的那種」，那是節奏軸的地盤。節奏判定為「一見傾心」時，畫面上會同時出現：

> 節奏：你們是**一開始就強烈吸引**的那一種。
> 摘要：你們**不是一見面就燒起來**的那種。

**發生率 8.8%**——每十二個使用者就有一個讀到。

**檢查**：`lint.js` R7（字表比對，已自動化）

### 規則 2　字表擋不住語意，人要再讀一次

**實例**：籤詩「有些緣分沒有故事，只有日子」通過所有自動檢查——沒有任何禁用字。但配上「轟轟烈烈：你們是撞上的那一種」，那明明就是故事。

**檢查**：**人工**。補完文案必須把八種節奏並排讀一次。

## 二、跨軸一致性

不同軸各算各的，但有些組合不可能同時成立。

### 規則 3　沒有推力就不能說機會很高

格局判定為 `quiet`／`blank`／`plain`（無推力），或日干比和（兩個人都在等）時，**機會不得落在最高階**。

**為什麼**：否則會出現「你們沒有特別強的推力」配「條件都在」。

**檢查**：`chance.js` 的 `noPush` 約束（已自動化）。八萬組驗證，矛盾 0。

### 規則 4　指數與機會不同向時要交代

緣分指數看的是**這段緣本身的質地**，機會看的是**能不能走到一起**。兩者可以背離——底子普通但阻力少的組合，常比底子好卻卡住的更容易成。

**但讀者不知道**，不說明就會被當成前後不一。

**檢查**：`chance.js` 的 `note`（已自動化，雙向都有）

### 規則 5　期待與實際錯開時要橋接

「緣的重量」講**這段關係實際的力道**，「夫妻宮」講**你天生期待什麼**。實測 **83.6%** 的組合兩者不同。

不同不是錯——那是最有內容的地方。但要明說，否則「你主導」跟「你容易在意他的反應」讀起來像打架。

**檢查**：`palace.js` 的 `PAL_BRIDGE`（已自動化）

### 規則 6　橋接句不得斷言另一軸的內容

**實例**：我第一版的橋接句寫「這段關係的節奏不在你手上」，但那組實際是「他在給」不是「他主導」——**只依自己的夫妻宮就去斷言對方的狀態是不對的**。

橋接句只能點出「有落差」，並要讀者回頭對照前一段，不能描述那一段的內容。

**檢查**：人工。寫橋接句時問自己：這句話在另一軸的**每一種**判定下都成立嗎？

### 規則 7　建議不得互相抵銷

同一份報告不得同時出現「該你先開口」與「該先動的不是你」。

**現況**：「主動方」講已經發生的事，「下一步」講接下來該做什麼——**兩者常常不是同一個人，而那正是重點**（先動心的人未必該再主動）。所以這兩段不衝突，但寫新內容時要守住這條界線。

**檢查**：人工

## 三、判讀的誠實

### 規則 8　差距不足就不要指名

三個維度的最低分與次低差距不足 8 分時，**不得斷言「真正卡住你們的是 X」**。

**為什麼**：實測 10.9% 的情況兩者只差 0–2 分，那時候指名是硬掰。**34.5%** 的組合會走「盤上沒有明顯的短板」這條。

敢說「沒有」的判讀，才會讓人相信說「有」的時候是真的。

**檢查**：`shape.js` 的 `GAP = 8`（已自動化）

### 規則 9　分數不決定敘事

前三段由盤面**配置**決定，不由分數排名決定。分數只用來排名與呈現。

**檢查**：`shape.js` 的十種格局（已自動化）

### 規則 10　不得下無法驗證又會造成傷害的斷言

**不做**：

- 斷言對方有第三者（日柱只有 60 種，說錯了使用者會去查對方手機）
- 判使用者人格缺陷（「曖昧＝主體性缺失」那類）
- 斷生死災厄

**可以做但要留分寸**：局勢類的判斷（例如劫財爭合），且必須附上「被爭奪不代表會被搶走」這類界線。

**檢查**：人工。判準是——**如果這句話說錯了，她會做出什麼？** 會去翻手機、會自我否定的，就不寫。

### 規則 11　沒有把握的層次不要硬做

旺衰與喜用神是八字裡最沒共識、最容易算反的一步。**判反了，「一見鍾情」的判定會整個顛倒——比不夠深還糟。**

在師資給出判準之前，只做不需要旺衰的判定（見 `ASK-PRACTITIONERS.md`）。

## 四、段落結構

### 規則 12　三截分工

```
open   建立語氣，不碰判斷      ← 可省略
core   下判斷，固定不可變       ← 這是分數的文字化
close  往前推一步：後果／趨勢／做法
```

**判準**：把 core 遮起來，open 應該還看不出結論；把 close 遮起來，core 應該還是完整的一句話。

**檢查**：`lint.js` R1、R3（已自動化）

### 規則 13　開場句只給最需要的那一段

三個維度都帶開場句，連讀就變公式。實測分佈：67.4% 的報告有一段帶開場句，**沒有任何一份會出現兩段以上**。

**檢查**：`copy.js` 的 `lowest` 邏輯（已自動化）

### 規則 14　重點句不得重述內文

「這一段的重點」是**提煉**，不是**highlight**。同一句話隔 60 字出現兩次，讀起來像填充不像強調。

**現況**：程式會移除內文裡與重點句重複的句子（45.6% → 14.5%）。剩下的要靠重寫重點句。

**檢查**：半自動。`report.js` 會去重，但根本解是寫的時候就不要重複。

### 規則 15　框架句彼此不得重複

`wrap.js` 的 66 句框架句共用於 16 個段落，**彼此之間也會撞**。

**實例**：`caution` 與 `values` 都寫了「知道它在哪裡」、`attitude` 與 `appearance` 都用「這一段講的是」——同一份報告裡會出現兩個一樣的開場。

**檢查**：`checkwrap.js`（已自動化，納入 `npm run lint`）

## 五、語氣

### 規則 16　機率描述用機率的語氣

判讀是機率，不是事實。「多半／通常／往往」不是保守，是準確。

**實例**：「你們多半是在一個需要長時間共處的環境裡認識的」——說中就是準，說不中她只會覺得這次不準，不會覺得被騙。寫成「你們是在工作場合認識的」，錯了就是錯了。

**例外**：干支表那一段用旁觀視角、不用機率語氣，因為它在建立可信度，語氣一親近反而弱掉。

## 檢查清單

改完文案之後，依序跑：

```bash
npm run lint     # R1–R7 共 1,356 組合 ＋ 全域名稱唯一 ＋ 框架句互撞
npm run build
```

三項都要看到 ✓：

```
檢查組合數：1356
全部通過 ✓
全域名稱無衝突 ✓（177 個識別名）
框架句無互撞 ✓（66 句）
```

括號裡的數字會隨程式長大而變，不用跟這裡一模一樣，看到 ✓ 就對了。
`npm run lint` 之外還有一支 `npm run accept`，跑的是驗收基準組
（72／一見傾心／他先動心／21 段那一組），確認引擎沒有算歪。兩支都要過。

然後**人工做這四件事**：

1. 抽三到五組完整輸出從頭讀到尾
2. 把新文案配上八種節奏並排讀一次（規則 2）
3. 確認新的框架句沒有跟現有 66 句重複（規則 15）
4. 問自己：這句話說錯了，她會做出什麼（規則 10）

**六條靠人。** 這不是偷懶，是這幾條的判準本來就在語意層——字表擋得住字面，擋不住意思。

建議補的自動檢查（優先序）：

1. **機率語氣**（規則 16）——掃描判讀句是否含「多半／通常／往往」
2. **建議互斥**（規則 7）——列出互斥詞對，掃描同一份報告
