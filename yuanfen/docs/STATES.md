# 緣分指數 · 狀態與情境總表

寫文案之前要先把狀態列完，否則會發生兩件事：漏掉的狀態沒有對應文案，出現頻率極低的狀態卻花了同樣力氣寫。

---

## 一、引擎狀態（已實作）

### 各維度的 key 與實際出現率

| 緣的溫度（日支） | 出現率 | | 緣的重量（日干） | 出現率 |
|---|---|---|---|---|
| `ping` 無刑衝合 | **46.2%** | | `a_ke_b` 你握話語權 | 20.6% |
| `sanhe` 三合 | 16.7% | | `a_sheng_b` 你在給 | 20.5% |
| `liuhe` 六合 | 8.6% | | `bihe` 力量對等 | 20.3% |
| `liuchong` 六沖 | 8.2% | | `b_ke_a` 他握話語權 | 19.6% |
| `liuhai` 六害 | 8.0% | | `b_sheng_a` 他在給 | 19.0% |
| `same` 同支 | 5.3% | | | |
| `xing` 相刑 | 4.2% | | **重量五種幾乎均分**，每一種都要寫好 |
| `zixing` 自刑 | 2.8% | | | |

長度（年支）分佈與溫度幾乎相同（`ping` 47%、`sanhe` 15.7%）。

### 分數帶

| | 出現率 | 意義 |
|---|---|---|
| 緣暖 | **43.5%** | 主力 |
| 緣淡 | **40.5%** | 主力 |
| 緣薄 | 8.3% | |

### 寫作資源分配

**八成的使用者會落在「緣暖」或「緣淡」，而且溫度／長度有近半是 `ping`。**

這代表：

- `ping` × 緣暖／緣淡 是最該寫深的組合，卻最容易被寫得敷衍（因為它「沒什麼特別」）
- 緣滿只有萬分之三會看到，但**不能不寫**——拿到的人一定會截圖分享
- 重量五種均分，任何一種寫壞都會影響兩成使用者

實際出現的三維度 × 分數帶組合：**548 種**（理論上限 1920，因為分數與 key 相關，不是獨立的）。

## 二、使用者情境（未實作，這是缺口）

**目前所有文案都預設「已經在一起」。** 「他在這段關係裡」「你們相處」這些句子，套在下面幾種情境會出戲：

| 情境 | 目前文案的問題 | 預估佔比 |
|---|---|---|
| **曖昧中** | 「這段關係裡」——還沒有關係 | 高 |
| **單戀／暗戀** | 「你們相處」——可能根本沒相處過 | 中 |
| **交往中** | 沒問題，目前寫的就是這個 | 高 |
| **分手後** | 「接下來會發生什麼」——語氣完全不同 | 中 |
| **已婚／同居** | 「他對長期關係看重什麼」——已經在長期關係裡了 | 低 |
| **朋友／同事** | 全部愛情語彙都不適用 | 低 |

你的 610 支籤在工作類已經做過同樣的事——分五個情境（迷惘中／求職中／轉職中／職場中／創業中），籤號 14–74 在五個情境各有一版。合盤應該沿用同一套邏輯。

### 建議收斂成四個情境

| 情境 | 涵蓋 | 稱謂與語氣調整 |
|---|---|---|
| **曖昧中** | 曖昧、剛認識、有好感 | 「你們之間」取代「這段關係裡」；不預設已有承諾 |
| **交往中** | 交往、同居、已婚 | 現行文案，不用改 |
| **分開了** | 分手後、冷淡期、失聯 | 改用過去式與「還有沒有可能」的框架 |
| **說不上來** | 單戀、朋友以上、複雜 | 最中性的措辭，避免所有關係定義 |

**不要做六個。** 已婚跟交往中的差別在文案上不大，朋友／同事的量太小，為它們各寫一版不划算。

### 實作成本

情境是**第五個維度**，但它不參與計分——只影響措辭。作法是每個 `core` 各寫四個情境版本：

```js
core: {
  曖昧:   '你們之間現在⋯',
  交往:   '這段關係裡⋯',      // 現有的
  分開:   '你們之間曾經⋯',
  未定:   '你和他之間⋯'
}
```

21 個 key × 4 情境 = 84 個 core（現在是 21 個）。open／close 大部分可共用，只有含關係預設的句子要分版。

**估計要新寫 63 個 core 加上約 40 句需要分版的 close。**

## 三、還沒處理的邊界狀態

| 狀態 | 現況 | 建議 |
|---|---|---|
| 同一天生日（雙方完全相同） | 會算出高分，文案讀起來像在講一個人 | 加一句特別的識別 |
| 相差 20 歲以上 | 沒有任何處理 | 年齡差不影響算法，但文案可以避開「同步」類措辭 |
| 生日在 2/3–2/5 | 年柱可能差一年 | 補立春精確表 |
| 未來的生日 | 目前只擋 1900–2100 | 應擋掉未來日期 |
| 雙方性別 | 完全不收 | 稱謂目前寫死「他」，同性伴侶會出戲 |

**性別那項值得優先處理。** 只要一個下拉（他／她／對方），影響的是整份報告的每一個代名詞，成本低但體感差很多。

---

## 四、建議順序

1. **性別稱謂**——一個下拉，改 `names` 參數就好，半天
2. **四個關係情境**——這是最大的一塊，但也是最能提升準確感的
3. **邊界狀態**——同生日、未來日期、立春表
4. 其餘文案擴充

第 2 項做完之前，不建議再擴充現有 key 的變體數量——因為情境分版會讓每一句都要重寫一次。
