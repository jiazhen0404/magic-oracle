### 1　生日不放在回跳網址上　✅ 已定案

施工單原本寫的是把生日編碼進回跳網址：

```
/yuanfen/?paid=<orderNo>&a=19910404&b=19871230&ha=9&hb=21
```

**不採用。** 那樣寫「不進資料庫」是真的，但生日仍然會外流到：

| 誰會拿到 | 途徑 |
|---|---|
| Google Analytics | GA4 自動送 `page_location`，含完整 query string |
| 綠界 | 回跳時的 Referer |
| 瀏覽器歷史紀錄 | 明文留存 |
| 任何被分享的連結 | 貼給朋友就洩漏兩個人的生日 |

而頁面上寫著「除非你主動送出準確度回饋，否則兩組生日不會離開這一頁」。

**改成：** 生日存 `localStorage`，以訂單編號為 key；回跳網址只帶
`?paid=<orderNo>`。同一個瀏覽器付款、回跳，localStorage 必然還在。
換裝置開回跳連結會還原不了，那時請使用者重新輸入生日即可——
計算是免費的，付費解鎖的是報告本身。

### 2　比照 99 元強制勾選同意條款　✅ 已定案

延伸籤的 `createOrder` 有這段強制檢查，合盤要比照：

```js
// 法規要求：數位內容不適用七日解除權，必須留下「事先同意」的證據
if (consent.terms !== true || consent.digitalContent !== true) {
  return json({ error: 'consent_required' }, 400);
}
```

合盤同樣是在台灣銷售的數位內容，同意時間要存進訂單。

| 決定 | 原因 |
|---|---|
| 早子／晚子採**子初換日**（23:00 後日柱算次日） | 市面常見排盤的預設是 23 點換日。日柱是本產品最吃重的一根柱（夫妻宮＝日支、溫度＝日支關係、重量＝日干），對不上等於整份判讀對不上 |

## 2026-09-12　抽籤當下就記錄生日（推翻先前決定）

**原本**：抽籤完全在裝置上算，不呼叫任何 API；只有使用者主動送出準確度回饋時，
兩組生日才會離開瀏覽器。頁面與條款頁都這樣寫，並有自動測試守著。

**改成**：按下測算的當下就建立一筆合盤紀錄（`reading_id` ＋ 兩組生日 ＋ 結果快照），
存進 KV，保留 12 個月。

**為什麼**：校準活動要算「抽了但沒填問卷」的分母。那個數字放在 GA4 裡不夠用——
GA4 算得出人數，但接不回「這個人當時看到的是哪一份合盤」。
負責人 2026-09-12 在明知會動到隱私承諾的情況下拍板。

**連帶改了三處說法，三處必須一致**：

| 位置 | 改成 |
|---|---|
| `yuanfen/index.html` 的 `.privacy` | 測算會把兩組生日記錄下來…保留 12 個月後自動刪除 |
| `privacy/index.html` 第 152 行 | 按下測算的當下就會留下 |
| `privacy/index.html` 第 163 行 | **沒改**，保留 12 個月那句本來就正確 |

**測試也換了，不是刪掉**。`ga-check3.js` 原本守「起盤不呼叫任何 API」，
現在守新的承諾：起盤只能呼叫 `/api/yuanfen-reading` 一支，
且送出的內容不得含信箱或姓名。

**要再改回去的話**：三處說法、測試、`registerReading()` 要一起改，
少改一處就會變成「說的跟做的不一樣」，那比兩種狀態都糟。

### 沒有採用的替代方案

`reading_id` 在瀏覽器產生、只在送出問卷時才連同生日上傳。
那樣能同時滿足綁定需求與原本的承諾，代價是看不到「抽了但完全沒碰問卷」的人。
提出過，負責人選擇前者。
