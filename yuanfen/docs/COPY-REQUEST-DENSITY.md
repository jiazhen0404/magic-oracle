# 文案需求：提高資訊密度

## 這份要解決什麼

負責人 2026-09-12 的評語：**「這整份解讀像是在塞文字，太空泛。字很多，但資訊量很小，重點很少。」**

這不是語感問題，是可以量出來的。以下數字都來自實測，不是感覺。

---

## 先排除一個常見的猜測

**問題不是「每個人拿到一樣的字」。**

實測 400 組「兩份毫不相干的盤」逐段比對，平均重疊只有 **21.5%**，
而且 **25 段裡沒有任何一段超過 50%**。文字確實有差異化。

**問題在密度，不在重複。** 底下三條才是真正的原因。

---

## 原因一　41% 的句子在講「不是什麼」　★ 最重要

38 萬句抽樣，**四成含否定詞**（沒有／不是／不會／不太／未必）。

典型的例子（免費頁「緣的溫度」）：

> 你們之間**沒有**特別強的火花，也**沒有**明顯的不對盤。相處是舒服的，只是**還沒有**非見不可的拉力。

一句話三個否定。讀者讀完知道「不是什麼」，但拿不到一個可以想的東西。

### 要怎麼改

**把否定句翻譯成肯定句。同一個判斷，換一個說法。**

| 現在（否定） | 改成（肯定） |
|---|---|
| 你們之間沒有特別強的火花 | 你們是慢慢熱起來的那一種 |
| 也沒有明顯的不對盤 | 相處起來是順的 |
| 只是還沒有非見不可的拉力 | 缺的是一個非見不可的理由 |
| 他不太表達 | 他習慣用做的，不是用講的 |
| 沒有哪一個明顯拖累其他兩個 | 三項的力道差不多 |

**判準**：一句話唸完，讀者腦中要出現一個畫面或一個可以對照自己的具體情境。
如果只留下「所以到底是怎樣」，那句就要重寫。

**不是要完全禁止否定句。** 有些判斷本來就是「缺什麼」，那時候否定是準確的。
目標是把 41% 壓到 **25% 以下**。

---

## 原因二　有三段經常沒東西可講

這些段落**不管判不判得出結論都會出現**。判不出來時，它只能講原則——那就是填充。

| 段落 | 落在「沒東西可講」分支的機率 |
|---|---|
| 只有你們兩個人的時候，是什麼樣子？ | **46.8%** |
| 明明有感覺，為什麼就是差那一步？ | **36.3%** |
| 你們想要的愛情，真的是同一種嗎？ | **33.6%** |

實際長出來的樣子：

> 盤上沒有單一的短板。三個項目各有各的狀況，但沒有哪一個明顯拖累其他兩個。
> 這種情況下不用急著找問題——真正該問的是你們想把這段關係帶去哪裡。
> 找到它不代表就解得開，但至少你不會再往錯的方向使力。

150 字，沒有一句是關於這兩個人的。

### 要怎麼改

**這一項由工程處理，不用寫文案**——判不出結論就整段不顯示。

但寫新文案時要守住同一條原則：**沒有結論的時候，不要用原則填滿。**
寧可那一段消失，也不要留一段誰都適用的話。

---

## 原因三　一個判斷被攤成 230 字

整份報告 24 段、約 3,000 字，但底層只有 **13 個判斷值**在驅動。
平均每個判斷被寫成 **230 字**。

單段最長 247 字。

### 要怎麼改

**每段壓到 80–100 字。**

短不會讓它變空泛，**長才會**——因為長度是靠原則句和否定句撐出來的。
刪掉那些，剩下的就是真正的判斷。

**具體做法**：每段留一句判斷、一句後果、一句可以做的事。三句講完。

## 硬規則（沿用既有的，不要違反）

這些寫在 `yuanfen/docs/RULES.md`，每一條都是實際踩過的坑。

### 1　不准跨軸下斷言

每個軸只回答自己那件事：

| 軸 | 只能回答 |
|---|---|
| 分數帶 | 這段緣有多深、多有份量 |
| 節奏 | 你們是怎麼開始的 |
| 三維度 | 溫度／重量／長度各自的狀況 |
| 機會 | 走到一起的機會多大 |
| 主動方 | 誰先動心 |

**實際踩到的例子**：「緣的溫度」寫了「沒有特別強的**火花**」（火花是節奏的地盤），
而節奏判定「一見傾心」時，6.9% 的使用者會同時讀到這兩句，當場矛盾。
另有「沒有明顯的**不對盤**」與格局的「有一處明顯的摩擦」相撞，1.0%。

**目前已知要改的 6 句**（`copy.js` 與 `shape.js`）：

1. `copy.js` 緣的溫度 `ping.core.曖昧`：「沒有特別強的火花，也沒有明顯的不對盤」
2. 同上第二句：「不會卡，也沒有那種強烈的拉力」
3. 同上第三句：「相處起來沒什麼問題」
4. `copy.js` 緣的溫度 `ping.core.未定`：「也沒有明顯的排斥」
5. `copy.js` 緣的溫度 `po.close`：「一開始就沒講清楚的期待」
6. `copy.js` 緣的長度 `xing.close`：「一開始就順的關係」

### 2　不准暗示第三者

不可以寫「有人跟你競爭」「他身邊還有別人」或任何會讓讀者去查對方手機的句子。
日柱只有 60 種，說錯了使用者會做出無法挽回的事。

### 3　不准判人格缺陷

描述**狀態**，不評價**人格**。不可以寫「你太依賴」「你的問題是沒有主體性」。

### 4　機率語氣要保留，但不要每句都用

「多半／通常／往往」不是保守，是準確。但目前 15.8% 的句子帶機率語氣，
**其中 6.5% 同時又是否定句**——「多半不會」這種寫法等於什麼都沒說。

否定句和機率語氣**不要出現在同一句**。

### 5　不用術語

不要出現「日支」「日干」「納音」「盤面」「配置」「本命」這類字。
使用者看到的應該是關係的樣子，不是命理的名詞。

**實際踩到的例子**：`flavour.js` 寫「你這個人像**路旁土**——不顯眼，卻是所有人走過的地方」，
納音術語直譯，使用者看不懂，而且「路旁土」是負面聯想。

## 語氣

**好的樣子**（現有文案，可以當標準）：

> 你們之間的東西是紮實的。不是最濃的那一級，但它有厚度——不容易被小事動搖，也不容易憑空消失。

> 訊息裡很熱，見面就變冷。這種落差通常不是他裝的，而是他在文字裡比較敢，面對面反而退回去。

**不好的樣子**（現有文案，要改掉的）：

> 這種情況下不用急著找問題——真正該問的是你們想把這段關係帶去哪裡。找到它不代表就解得開，但至少你不會再往錯的方向使力。

差別：前兩句給得出畫面，第三句只給原則。

其他：

- 第二人稱「你」，對方一律寫 `{B}`（程式會依使用者選擇替換成他／她／對方）
- 不安慰、不勸世、不下指導棋
- 句子可以短。不要為了文氣堆疊子句

---

## 交件格式

**直接改原檔**，維持原本的 key 與結構，只換字串內容。
不要改變 key 名稱、不要增刪分支——那會動到程式邏輯。

如果某一個 key 你覺得應該拆成兩種或合併，**先說，不要自己改**。

---

## 驗收標準

交件後會跑自動檢查：

1. **否定句比例 < 25%**（目前 32%，`copy.js` 33%）
2. **沒有跨軸斷言**（`lint.js` R7 的字表）
3. **沒有命理術語**
4. **否定句與機率語氣不同句**
5. **單段字數 ≤ 100**
6. 既有的 R1–R7 全部通過（`npm run lint`）
7. 驗收基準組不變（`npm run accept`）

另外**人工讀一次**：隨機抽五份完整報告從頭讀到尾，
問自己一個問題——**「這段話如果說錯了，讀者會發現嗎？」**
如果不會，那句就是空話。
