# 緣分指數 · MVP 規格

未完籤所雙人合盤產品線的免費層。輸入兩人西元年月日，輸出總分＋三個子維度＋文案＋可分享卡。

## 為什麼不用月柱

原本規劃「月支＝相處節奏」，但月柱要靠節氣定界，得內建一整套節氣表或外掛曆法套件。改用**日支**取代：日柱可用儒略日直接算出，精確且零資料表，同時提供日干（給緣的重量）與日支（給緣的溫度）。整套只剩年柱需要立春界線。

## 三個子維度

| 維度 | 資料來源 | 講的是 | 權重 |
|---|---|---|---|
| 緣的溫度 | 日支關係 | 日常相處合不合 | 35% |
| 緣的重量 | 日干五行生剋方向＋陰陽 | 誰在承擔、誰在退讓 | 30% |
| 緣的長度 | 年支關係(60%)＋年柱納音(40%) | 這段關係能走多遠 | 35% |

「緣的重量」的方向性是刻意保留的：A生B 與 B生A 分數相同但文案完全不同，這是整張卡最像「為你量身」的地方。

## 校準結果（20 萬組模擬，生年 1991–2001 × 1985–2005）

```
平均 69.4 ／ 中位 70 ／ 標準差 8.4 ／ 範圍 43–94

90+    緣滿·春暖花開   0.5%
80-89  緣濃·花好月圓   9.6%
70-79  緣暖·細水長流  40.1%
60-69  緣淡·雲淡風輕  37.1%
50-59  緣薄·聚散有時  11.3%
<50    緣散·各自天涯   1.4%
```

六階名稱在同一條濃度軸上（滿→濃→暖→淡→散），配四字副標。`render()` 回傳 `label`、`title`、`headline`（＝「緣暖·細水長流」）三個欄位，分享卡直接取 `headline`。

90 分以上約 200 組出現 1 次——夠稀有，拿到的人會想截圖。50 分以下 1.4%，低分不會常見到麻痺。

要調的話**只動 `zhiRelation` 的分數常數、`ZHONGLIANG_BASE`、`NAYIN_SCORE`、`WEIGHTS`，不要動公式**，改完重跑 `node calibrate.js`。

## 已知誤差

1. **立春以 2/4 近似**，實際落在 2/3–2/5，每年不同。生日在 2/3–2/5 的使用者年柱可能差一年。要修的話補一張 1900–2100 的立春日期表（每年一個位元組即可）。
2. **納音以 30 為週期**簡化，已用八組六十甲子驗證過。
3. 未處理出生時區與跨日邊界——年月日層級不需要。

## 還要你決定的

- **權重**：目前 35/30/35。加重「緣的重量」會讓方向性文案更常成為主軸，但分數分佈會變窄。
- **低分怎麼收**：現在 `緣逆` 那段直接寫「先問自己那個人是不是你」。這符合你敢命名難堪狀態的調性，但雙人產品的低分是會被拿去給對方看的，語氣要不要再收一點由你判斷。
- **文案還沒過你的流程**：這批是照你籤文語感寫的初稿，照慣例應該進你的修稿流程再上線。

## 分享卡與隱私

- 卡片建議在 Worker 端直接生成 SVG，總分＋標籤＋三個子分數即可，內文留在頁面上。
- 頁面要明寫**不儲存對方生日、算完即丟**。演算法是純函數，本來就不需要落地任何資料——這句話寫得出來，也真的做得到。

## 文案變體機制

每段拆成三截：

- **`core` 判斷句 —— 固定，不可做成變體。** 這是分數的文字化，變了等於分數在跳。
- **`open` / `close` 包裝句 —— 可變。** `close` 必須帶預測或具體做法，不能只是收尾。

變體用兩人生日雜湊出的種子抽選（`seedOf`），所以同一組永遠得到同一句，A×B 與 B×A 也相同。每個欄位有自己的 salt，不會整張卡一起變。

要加句子就往 `open` / `close` 陣列裡塞，邏輯不用動。目前每個 key 各 2–3 句，籤語各 3 句。

`render()` 簽名多了 birth 參數：

```js
render(yuanfen(a, b), { a, b })
```

自檢過的三件事：重複呼叫結果完全相同、種子與 A/B 順序無關、不同組會抽到不同變體。

## 算式揭露

免費卡要把分數算給使用者聽，否則「有一項 90 為什麼總分才 73」會變成客訴來源。

```js
const { renderBasis, gapNote } = require('./basis');
```

`renderBasis()` 輸出三段：每個維度的**依據**（實際干支）、**判定**（三合／相剋／納音相生）、**權重**，最後一行是加權算式。目的不是教命理，是讓分數看起來有來歷。

`gapNote()` 在最高與最低維度相差 22 分以上時，回一句點破落差的話。實測 59.7% 的組合會觸發，六種落差方向的分佈平均（6–16%）。門檻在 `GAP_THRESHOLD`，調高會讓提示更稀有但更有份量。

這句話是免費層最有價值的一句，而且零成本：它把「分數」變成「診斷」，也自然帶出「那我該怎麼辦」——那正好是付費層要回答的。

## 時辰（付費層）

`yuanfen(a, b)` 的 a／b 可多帶 `hour`（0–23 的整數）。**雙方都給才啟用**，只有一方給等於沒給。

```js
yuanfen({y:1991,m:4,d:4,hour:9}, {y:1986,m:12,d:30,hour:21})
// → hasHour: true，dimensions 多出 midu
```

時支由小時直接對照（23:00–00:59 為子），時干用五鼠遁從日干推（甲己起甲子、乙庚起丙子、丙辛起戊子、丁壬起庚子、戊癸起壬子）。**不需要任何新資料表。**

第四維度 **緣的密度** = 時支關係(60%) ＋ 時干五行(40%)，講的是私下相處的樣子。時柱在傳統上主晚年與私密面，對應到雙人就是「關起門來是什麼樣子」——這正好是免費層完全看不到的角度。

權重在有時辰時重新分配：

| | 三維（免費） | 四維（付費） |
|---|---|---|
| 緣的溫度 | 35% | 28% |
| 緣的重量 | 30% | 24% |
| 緣的長度 | 35% | 28% |
| 緣的密度 | — | 20% |

15 萬組模擬：四維總分平均 69.5、中位 70、範圍 45–92，與三維版幾乎同一條分佈（差值中位 0，95% 落在 ±5 內）。這是刻意的——**付費後分數不應該大幅跳動**，否則使用者會覺得免費那個是假的。

### 已知限制

- **早子時／晚子時**：目前 23:00 之後算當日子時，日柱不跨日。部分流派會把 23:00 後的日柱進到隔天，若要支援需在 `pillars` 加開關。
- **不知道時辰**：一定要有 fallback。建議做法是保留三維結果，不要用「不知道就算中午」——那會產生一個看起來精確但其實是猜的分數。
- **宮位合盤仍未實作**。安紫微星需要農曆日與五行局，得先有西元轉農曆的對照表，且各派安星法不同，要先鎖定流派。時柱只是四柱層級，不等於宮位。

## 時辰選擇與隱藏規則

時辰是每個人一個下拉選單，共 14 個選項：

```
出生時辰            ← 預設（佔位，不可送出）
不確定時辰
子時　23–01
丑時　01–03
…
亥時　21–23
```

「不確定時辰」排在時辰清單之前，不用捲到底才找得到。地支和時間範圍並列，使用者不必自己換算。下拉在手機上是原生轉輪，比一排按鈕好按，也不占版面。

**免費層的三個維度與總分永遠不受時辰影響。** 時辰只決定付費區塊要不要提到第四個維度：

| 狀態 | 免費結果 | 付費清單提到「緣的密度」 |
|---|---|---|
| 雙方都選了時辰 | 三維，分數不變 | 是 |
| 一方不確定 | 三維，分數不變 | 否 |
| 雙方都不確定 | 三維，分數不變 | 否 |
| 都沒選 | 三維，分數不變 | 否 |

沒有時辰時「緣的密度」在畫面上完全不出現——不是反灰、不是加鎖，是不存在。看見一扇打不開的門比看不見更糟。

沒有時辰時，結語會多一句「沒有時辰不影響上面的結果」，避免使用者以為自己拿到的是缺角版本。

**不要用「不知道就算中午」補值。** 那會產生一個看起來精確、其實是猜的分數，而且一定會有人拿去跟朋友比對。

已用 jsdom 測過四種狀態：分數在四種情況下都是 73，「密度」字樣只在雙方都給時辰時出現。

## 免費／付費的分界線

分界不在字數，在**顆粒度**：

| | 免費 | 付費 |
|---|---|---|
| 走勢 | 趨勢（會變嚴重、會反覆出現） | 事件（什麼時候、以什麼形式、之後會怎樣） |
| 對方視角 | 幾乎沒有 | 完整一段 |
| 時間層 | 沒有 | 近期／中段／之後 |

原本免費層有 14 句寫成了具體事件（「接下來他會有一次反常的堅持…」），等於把付費層的內容先給完。這批已全部改寫成趨勢版，原句移到 `events.js` 當付費素材。

免費頁正文中位數 391 字，改寫前後幾乎沒變——**要調的是內容類型，不是長度**。免費層仍然自成完整：診斷在、落差句在、走勢方向在。

`eventsFor(result, band)` 依總分帶與三個維度的 key 取出適用事件，每組 3–5 句、135–250 字。這是付費報告「接下來會怎麼發展」那一段的骨架，不是完稿——完稿要再展開三個時間層並補上對方視角。

改寫免費文案時的自檢：句子裡如果出現「會有一次」「會出現一件」「接下來他」，多半已經越線，該搬到 `events.js`。

## 「對方現在怎麼想」的組裝方式

這一段看起來最個人化，實際上只由**緣的重量**決定主線——因為只有那個維度有方向性（誰在給、誰握話語權）。溫度和長度講的是「你們」，講不出「他」。

拆成三層，三層必須正交，否則接起來會有拼裝感：

| 層 | 由誰決定 | 字數 | 段數 | 講什麼 |
|---|---|---|---|---|
| 位置 | 重量 key | 200 | 5 | 為什麼 |
| 樣子 | 溫度 key | 120 | 8 | 你看到什麼 |
| 態度 | 長度 key | 80 | 8 | 他打算怎樣 |

5 × 8 × 8 = **320 種組合**，只要寫 21 段。

`other-position.js` 是第一層（5 段，225–253 字），`other-appearance.js` 是第二層（8 段，101–119 字），都已完成。寫另外兩層時的自檢：位置層不該出現「你會看到」，樣子層不該解釋原因，態度層不該描述行為——一旦跨層，組裝時就會重複。

整份 1,850 字的付費報告，實際要寫的模組約 60 段。比逐盤寫少兩個數量級。

## 付費報告（預覽模式）

`report(result, names)` 回傳七個段落（無時辰為六段，缺「緣的密度」）：

| 段落 | 由誰決定 | 實測字數 | 原訂目標 |
|---|---|---|---|
| 這段緣現在停在哪裡 | 分數帶 ＋ 最低維度 ＋ 最高維度 | 246 | 300 |
| 對方現在怎麼想 | 重量 ＋ 溫度 ＋ 長度（三層） | 427 | 400 |
| 緣的密度 | 密度 key（僅雙方給時辰） | 150 | 250 |
| 接下來會怎麼發展 | 分數帶開場 ＋ events ＋ 收束 | 309 | 500 |
| 可以觀察的變化 | 重量 key，7 條 | 113 | 150 |
| 需要留意的地方 | 最低維度 | 181 | 250 |
| 你現在適合怎麼做 | 重量 key | 162 | 250 |

**實測分佈（4000 組模擬）：**

```
無時辰　1,432 – 1,705　中位 1,547
有時辰　1,556 – 1,937　中位 1,750
```

頁面上的字數口徑因此寫成「有時辰約一千八百字／無時辰約一千五百字」，這是可以被客人數出來的數字。要改口徑就改 `draw()` 裡 `$('u-price')` 那一行——但改之前先跑一次模擬，不要寫一個抽查會被抓到的數字。

有時辰的組合只有 35% 真的達到 1,800，中位是 1,750。「約」撐得住，但如果要讓多數組合超過 1,800，還得再補約 100 字，最有效的位置是「可以觀察的變化」（目前 113 字，可加到每項一句短說明）。

網頁上按「閱讀完整合盤」直接展開，**尚未接金流**。重新起盤時報告會自動收合、按鈕還原。上線前要把這個按鈕換成付款流程，並移除按鈕下方的預覽說明。

## 分享卡

在**瀏覽器端用 canvas 畫**，不在 Worker 端生 SVG——Worker 上中文字型無法內嵌，會變成方框。

素材路徑寫死在 `card-render.js` 的 `CARD.ASSET`，預設 `assets/medallion.png`。這張是我用鏡射補掉右下角那個 `%` 的版本，**補得不乾淨（放射線被切斷、有一塊糊掉的方形），只能當版面確認用，正式上線請換成重新生成的乾淨素材。**

兩顆按鈕：

- **儲存圖片** — `canvas.toBlob` 後觸發下載，檔名帶分數
- **分享** — Web Share API 帶檔案；不支援的瀏覽器（多數桌機）會提示改用儲存

繪製前 `await document.fonts.ready`，否則 Google Fonts 還沒載完，canvas 會用系統預設字型畫出來。這一步不能省。

素材載不到時分享區塊整個隱藏，不會出現破圖。

### 踩過的坑

`(seed ^ Math.imul(...)) >>> 0 % arr.length` 是錯的——`%` 的優先序高於 `>>>`，實際被解析成 `seed ^ (x >>> (0 % len))`，抽出來永遠是 undefined。要寫成兩行，或把整個右移運算括起來再取模。

## 文案定位（對照競品調整過）

| 免費層全是「付費後解鎖」 | 「免費的部分不會遮任何一句話⋯付費的是更深的一層，不是被藏起來的那一層」（起盤按鈕下方的承諾區塊） |
| 放一張看不懂的命盤當權威 | 「我們不放一張你看不懂的命盤。要看依據，這裡是完整的算法」（算式摺疊區塊） |
| 開場假設你單身寂寞想結婚 | 「不需要你單身，也不需要你想結婚——只要有一段關係讓你想弄清楚」（首屏） |
| 要註冊、資料進他們的資料庫 | 「不用註冊，不用留 email。兩組生日不會被儲存，也不會離開你的裝置」 |

最後一條是**唯一他們無法複製的差異**——引擎是純函數、全在瀏覽器端算完，這句話寫得出來也真的做得到。改動引擎時要守住這一點：一旦有任何一次 fetch 把生日送出去，這句話就不能再寫。

付費區塊多了一句價格對照：「完整合盤 NT$199，約一千八百字。市面上單人的完整鑑定多在四百上下，這份算的是兩個人。」不點名，客人自己會對照。

沒有時辰時，結語補上「也不會少給你任何一段」，避免使用者以為自己拿到縮水版。

### 兩件刻意不做的

- **不做「？？」遮字。** 與「升級是邀請不是把內容藏起來」直接衝突，且會消耗已經到手的信任。
- **不放命盤圖。** 算式揭露已經做到同一件事而且更好——它解釋，命盤圖只是展示。

### 時辰只走付費路徑（重要）

`yuanfen()` 在雙方都給 hour 時會改用四維權重，總分因此會變（實測 73 → 67）。但免費層必須永遠是三維、分數不隨時辰變動，否則給了時辰的人會發現分數突然不一樣。

所以頁面在 `draw()` 裡**刻意不把 hour 傳進免費那次計算**：

```js
const freeA = { y: a.y, m: a.m, d: a.d };      // 免費：三維
const r = yuanfen(freeA, freeB);
last = { result: r, a: freeA, b: freeB, full: yuanfen(a, b) };  // full：四維，只給報告用
```

`report()` 吃的是 `last.full`，所以「緣的密度」那一段只在雙方都給時辰時出現。改動這段時要記得兩次計算是分開的——把它們合併成一次，免費分數就會跟著時辰跳。

## 目錄

付費區塊用編號目錄（`<ol>`，`counter-leading-zero`），每一項有標題＋一行說明。目錄的段落名稱與 `report()` 實際輸出的 `title` 一字不差，並且會隨時辰增減——已用 jsdom 驗證兩者完全一致。

改 `report.js` 的段落名稱時，`yuanfen-index.html` 的 `toc` 陣列要一起改，否則目錄會跟實際內容對不上。這是目前唯一需要手動同步的地方。

## 干支表

付費報告的第一段是雙方干支表（`pillarTable(result)`），四欄：柱名／你／對方／用在哪裡。

**只列實際參與運算的柱**——年柱、日柱、時柱（有給時辰才有）、年柱納音。**刻意不列月柱**，因為這套演算法沒有用到它；列出來會讓人以為有算，那就變成競品那種「放一張看不懂的盤充場面」。表格下方直接寫明這件事。

表格不計入字數統計（`report()` 的 `chars` 會略過 `table` 型別的段落），所以頁面上寫的一千八百字指的是純文字，客人數起來只會多不會少。

手機（<420px）隱藏「用在哪裡」那欄，只留柱名與雙方干支，避免擠成三行。

## 段落標題用問句

段落名稱全部改成問句（`report.js` 的 `title` 與 `yuanfen-index.html` 的 `toc` 同步）：

```
這份合盤，是從哪裡算出來的？
你們現在，停在哪裡？
他心裡，到底是怎麼想這段關係的？
關起門來，你們是什麼樣子？      ← 僅雙方給時辰
接下來會發生什麼？什麼時候？
他變了沒有？從哪裡看得出來？
什麼事，會讓這段關係悄悄壞掉？
現在你能做的，具體是什麼？
```

問句直接對上使用者腦子裡已經在轉的那句話，比「對方分析」這種名詞標題有力得多。

競品（靈魂配對，click108/J0670）用 19 條問句當鑑定項目，但其中十幾條都在換句話問「那個人怎麼想」，讀起來像湊數。我們維持八段，每一段問的是不同的事——**問句要多，但問題不能重複**。

標題來自 `report()` 的 `title` 欄位，所以改標題必須同時改兩個檔案，否則目錄與內容對不上（jsdom 已在測試中檢查一致性）。

### 目錄改由 report() 產生

目錄不再手寫。`draw()` 直接呼叫 `report()` 取出 `sections`，用標題查 `TOC_DESC` 補說明，段數與字數也一併算出來：

```js
const preview = report(last.full, { A: '你', B: '他' });
$('u-price').textContent = '完整合盤 NT$199，共 ' + preview.sections.length
  + ' 段，約 ' + (Math.round(preview.chars / 100) * 100) + ' 字。';
```

**這解掉了先前唯一需要手動同步的地方**——改 `report.js` 的段落標題，目錄會自己跟上，段數與字數也自動更新，不會出現「目錄寫 14 段、內文只有 8 段」這種事。新增段落時只要在 `TOC_DESC` 補一行說明；漏補的話說明會是空字串（測試有檢查 `說明缺漏` 數）。

**不要為了看起來多而湊到 19 條。** 湊到 19 就必須開始重複問「他怎麼想」，那正是競品那份清單最弱的地方，而且列了 19 條卻只輸出 14 段是不實陳述。

## 19 段（無時辰 18 段）

補上五段之後到 19。新增的不是湊數——**原本整份報告從頭到尾沒有一段在講使用者自己**，全在講對方與關係，這是真的缺口：

| 段 | 模組 | key | 段數 |
|---|---|---|---|
| 那你自己呢？你在這段關係裡的位置 | `SELF_POSITION` | 重量 | 5 |
| 你可能沒發現的，自己的那一面 | `SELF_BLIND` | 重量 | 5 |
| 你們看重的東西，一樣嗎？ | `VALUES` | 年支 | 8 |
| 同一件事，你們的解讀差在哪？ | `READING` | 日支 | 8 |
| 如果只能記住一件事 | `KEEP` | 分數帶 | 6 |

`SELF_POSITION` 與 `SELF_BLIND` 同 key 但不同層——前者講「你在做什麼」，後者講「你看不到什麼」，寫的時候不可互相重述。

第一段標題改為「你們的緣分總表」。

實測（4000 組）：

```

有時辰　2,132 – 2,482　中位 2,321　19 段
```

頁面顯示的段數與字數都是從 `report()` 算出來的，不是寫死的。

### 兩個踩過的坑

- **`pick` 名稱衝突。** bundle 把所有模組併到同一個作用域，`self-values.js` 的 `pick` 撞到 `copy.js` 的 `pick`，瀏覽器直接 `SyntaxError` 整支掛掉。新模組的函式命名要先確認全域沒有同名——已改為 `svPick`。
- **`build.js` 原本只認解構的 require。** `const SV = require('./self-values')` 這種寫法沒被剝掉，bundle 帶著 `require` 進瀏覽器就爆。regex 已放寬到兩種寫法都吃。

## 五部結構

19 段分成五個部分，`report()` 的每個 section 帶一個 `part` 欄位，目錄與內文都在 `part` 改變時插入部別標題：

```
第一部分｜先看你們的關係              01–04
第二部分｜他與你，各自在這段關係裡      05–09
第三部分｜你們為什麼會這樣相處          10–12
第四部分｜這段關係，接下來可能怎麼走     13–16
第五部分｜現在，你可以怎麼做            17–19
```

第 12 段帶 `needHour: true`，目錄上會顯示「需完整出生時間」小標。沒有時辰時該段整個不存在，編號自動往前遞補（18 段），部別標題不受影響——已驗證兩種狀態都是 5 個部別。

標題全部改成問句，而且是使用者會在心裡問的那種問法（「明明有感覺，為什麼就是走不近？」而不是「最低的維度是什麼」）。內部邏輯不變，只換說法——`NOW_WEAK` 還是 `NOW_WEAK`。

分部之後有個額外好處：**19 條不再讀起來像流水帳。** 五個部分各自回答一個大問題，客人掃過去會看到結構，不是看到一長串。

## 字型

三支 Google Fonts，全部 OFL 授權，**不需要子集化**——Google 依 unicode-range 分片，只送使用者實際需要的字。

```html
<link href="https://fonts.googleapis.com/css2?family=Cactus+Classical+Serif&family=Lato:wght@300;400;700&family=Noto+Sans+TC:wght@200..500&display=swap" rel="stylesheet">
```

以 CSS 變數管理，不要在個別選擇器裡寫死字型名稱：

```css
--serif: "Cactus Classical Serif","Noto Serif TC",serif;  /* 標題・籤文・等級名・報告小標 */
--sans:  "Noto Sans TC",system-ui,sans-serif;             /* 內文・表單・UI・含中文的標籤 */
--latin: Lato,system-ui,sans-serif;                       /* 純英文與純數字 */
```

判準：**只要字串裡有中文就不能用 `--latin`**，Lato 沒有中文字符，會 fallback 到系統字型，同一行出現兩種字體。「緣分指數　73」用 `--sans`，`unfinished.tw` 才用 `--latin`。

分享卡的 canvas 另有一份 `CARD_FONT`（`card-render.js`），三支對應相同。canvas 不吃 CSS 變數，改字型時兩邊都要動。

## 這一段的重點

每段底部一個框，一句約 20 字的收束。**不是摘要，是把整段壓成一句能記住的話。**

`report()` 會依同一組 key 掛上 `section.takeaway`，共 104 句（19 段各依自己的維度 key 展開）：

| 段 | 取自 | key 數 |
|---|---|---|
| 01 干支表 | 固定 | 1 |
| 02 / 13 / 14 / 19 | 分數帶 | 6 × 4 |
| 03 / 16 | 最低維度 | 3 × 2 |
| 04 | 最高維度 | 3 |
| 05 / 08 / 09 / 15 / 17 / 18 | 重量 key | 5 × 6 |
| 06 / 11 | 溫度 key | 8 × 2 |
| 07 / 10 | 長度 key | 8 × 2 |
| 12 | 密度 key | 8 |

6000 組模擬跑過，**零缺漏**，字數 8–26、中位 20。

寫作規則（之後補句子時沿用）：

- 不重述段落內容，要提煉出一句本身就成立的話
- 不用「總之」「因此」開頭
- 不下判斷式結論（「你們一定會分手」），留給讀者決定
- **每句都要能單獨截圖分享而不失去意義** —— 這是最重要的一條，也是這批句子的真正用途

改段落標題時 `takeaway.js` 的 `map` 也要改，因為它是用標題字串當索引。改完跑一次覆蓋測試確認沒有掉句。

### 起盤動畫

按下「起盤」後**不立即出結果**：羅盤全螢幕轉 1.8 秒 → 結果浮現 → 分數從 0 跑到目標值（700ms，ease-out cubic）。

```js
setTimeout(() => { cast.classList.remove('on'); reveal(a, b); },
           REDUCED ? 400 : 1800);
```

`prefers-reduced-motion` 時縮到 400ms 並直接顯示最終分數——**但保留那 400ms**，完全瞬間出現會讓人以為表單沒送出。

數字跑動是整個動畫的重點：它讓分數看起來是算出來的，不是查表查到的。已驗證最終值一定落在正確分數（jsdom 測試等到動畫結束再比對）。

- 視差捲動、每個區塊的淡入上浮、背景星星集體閃爍——理由見 `UI-PLAN.md`

## 文案變體密度（擴充後）

`open` 陣列原本全是空字串，等於只有 `close` 在變。補上開場句並各加一句 `close` 之後：

| | 擴充前 | 擴充後 |
|---|---|---|
| 緣的溫度 | 16 | **72** |
| 緣的重量 | 10 | **45** |
| 緣的長度 | 16 | **72** |
| 總分帶（籤語 × close） | 36 | **72** |

4 萬組隨機生日跑出 **5,365 種不重複的免費頁全文**。上限受限於維度 key 的組合數（8×5×8×6），不是文案不夠——要再往上就得增加判斷維度，不是加句子。

### 開場句的寫法

`open` 是「框住情境」的一句，不是內容的一部分：

```
先講一件你大概早就感覺到的事。   ← open
你們在一起的時候，時間會過得比較快⋯  ← core（判斷，固定）
這種順不是努力來的⋯              ← close（可變）
```

三截要**互相不重複片語**，否則接起來會出現同一句話講兩次。

### 重複檢查

擴充時踩到兩次同樣的坑：

1. 長度 `ping` 的 open 與 close 都寫了「沒有註定，也沒有阻礙」
2. 溫度 `liuhe` 的 open 與 close 都有「你大概自己也」

這種錯誤在單看陣列時完全看不出來，只有實際組裝才會浮現。加了一個 6-gram 重複檢查涵蓋所有 open × core × close 組合，補新句子時務必跑一次：

```js
// 檢查所有組合中是否有 6 字以上的共同片段
for (const op of v.open) for (const cl of v.close) check([op, v.core, cl]);
```

## 視覺調整（第二輪）

前一版看起來單薄的原因是**所有內容都貼在同一個平面上，沒有層次**。這一輪的處理：

### 加了什麼

- **鑲金邊區塊（`.panel`）** —— 表單、目錄、三個維度都放進有邊框、內陰影、四個小金角的容器。這是最有效的一項，把平鋪的內容變成有厚度的卡片。

## 語意重複的修正

使用者回報「句子很多重複」，實際看到的是這種：

> 關於能走多遠，**這一項的答案不在盤上**。這段緣**沒有先天的長度，也沒有先天的限制**。**沒有註定，也沒有阻礙**。

三句話講同一件事。6-gram 字面檢查抓不到，因為用詞完全不同——**問題是語意重複，不是字面重複**。

### 兩個成因與修法

**一、開場句在複述判斷。** 我原本寫的 open 有一半是 core 的換句話說。已全部改寫成純框架句，只負責建立語氣，不碰判斷內容：

```
先講一件你大概早就感覺到的事。       ← 框架，不含判斷
你們在一起的時候，時間會過得比較快⋯  ← core，判斷在這裡
```

**二、三個維度都帶開場句，連讀就變公式。** 而且我寫的開場句有一半以「這一項⋯」起頭，三段連讀等於同一句話講三次。

修法是結構性的：**開場句只給分數最低的那個維度用**。

```js
const lowest = ['wendu','zhongliang','changdu'].sort((a,b)=>d[a].score-d[b].score)[0];
compose(WENDU[key], seed, SALT.wendu, lowest === 'wendu');
```

這同時解決兩件事——去掉公式感，而且開場句自動落在最需要被點出來的那一段。實測分佈：67.4% 的報告有一段帶開場句，32.6% 完全沒有（該維度的 open 抽到空字串），**沒有任何一份會出現兩段以上**。

### 檢查工具的侷限

6-gram 字面檢查仍然要留著（它抓到過兩個真的重複），但**它不能取代人眼**。語意重複只有實際讀輸出才看得出來，補新文案時要抽幾組完整輸出讀過。

## 分享卡改為隱藏預覽

卡片預覽佔掉一大塊版面，但使用者真正要的只是存檔。canvas 改為視覺隱藏（保留在 DOM，`toBlob` 仍可運作），只留「儲存圖片」與「分享」兩顆按鈕，加一行說明卡片內容。

## 文案品質的機制化

補文案之後一定要跑：

```bash
node lint.js
```

窮舉所有 open × core × close 組合（目前 207 個），驗六條規則。詳見 `COPY-SPEC.md`。

第一次跑就抓到 4 類真的問題，包含使用者回報的那種「三句同義」。關鍵在 R2／R3 用**概念群**比對而不是字面——`CONCEPTS` 把「註定／命定／先天／不在盤上」歸為同一群，所以換句話說也擋得住。

**但規則檢查不能取代人眼。** 補完文案還是要抽三到五組完整輸出讀過，語意是否通順只有讀才知道。

## 變體擴充（第三輪）與一個量測錯誤

每個 key 再各加 2 句 close，總分帶各加一句籤語與一句 close：

| | 第一輪 | 第二輪 | 現在 |
|---|---|---|---|
| 緣的溫度 | 16 | 72 | **120** |
| 緣的重量 | 10 | 45 | **75** |
| 緣的長度 | 16 | 72 | **120** |
| 總分帶 | 36 | 72 | **120** |

`node lint.js` 339 個組合全數通過。

### 量測方式的錯誤

第二輪之後我用「4 萬組隨機生日」量不重複輸出，得到 5,365；第三輪加了變體之後再量，還是 5,365——看起來像文案沒有效果。

**其實是測試方法錯了。** 隨機生日產生器只涵蓋 20 年 × 12 月 × 28 日 = 6,720 個日期，配對後只有 5,371 組不重複，所以不重複輸出當然卡在 5,365。**瓶頸是取樣，不是文案。**

改用系統性取樣（跨年月日均勻掃描）之後：

```
取樣 15,120 組｜275 種 key 組合
同一 key 組合底下的不同全文：min 4  中位 24  max 627
```

**中位數 24 是關鍵數字**——它代表兩個人拿到同樣的盤面判斷時，讀到的文字有 24 種可能。這才是「朋友之間互測會不會撞文」的真正指標，總不重複數反而沒有意義。

以後量文案多樣性要看**同一 key 組合底下的變化量**，不要看總不重複數，後者會被取樣範圍蓋過去。

## 盤面風味層：讓不同的盤讀到不同的解讀

### 問題

前三輪擴充都在加變體，但變體是由**亂數種子**決定的。兩個人只要 key 相同，讀到的判斷就一樣——加再多句子也只是換句話說，不是「不同的命盤有不同的解讀」。

### 成因：算出來的資訊被丟掉了

引擎其實算出了完整干支，但計分只取關係與五行，**把識別度最高的部分丟了**：

| 算出來的 | 計分用到的 | 丟掉的 |
|---|---|---|
| 日干 甲／乙／丙⋯ | 只取五行（甲乙都當木） | 10 種天干的個性差異 |
| 年支 子／丑／寅⋯ | 只取關係 | 12 生肖 |
| 年柱納音 60 甲子 | 只取五行（海中金與劍鋒金都當金） | **30 種納音的意象** |

### 解法

`flavour.js` 讓這些資訊回到文字裡，各接一句在維度段落最後：

| 維度 | 取自 | 句數 | 講什麼 |
|---|---|---|---|
| 緣的溫度 | 使用者日支 | 12 | 你在關係裡的相處風格 |
| 緣的重量 | 使用者日干 | 10 | 你付出的方式 |
| 緣的長度 | 使用者年柱納音 | 30 | 這段緣的質地 |

納音那組最有價值，因為 30 個名稱本身就有意象：

> 你的本命是海中金——藏得深，要挖得夠久才露得出來。
> 你的本命是楊柳木——彎得下去，所以折不斷。
> 你的本命是覆燈火——你的光是給特定的人看的，不是給全場。

**這一層不參與計分，只影響措辭。但它綁在命盤上，不是綁在亂數上**——這是它跟前三輪擴充的根本差別。

### 效果

同一組 key（`ping|a_ke_b|ping`）的四張不同命盤，現在三段全部不同。系統性取樣 15,120 組，**15,119 組產出唯一全文**——幾乎每一張盤都讀到不同的東西。

風味層可辨識的命盤特徵：日柱 60 × 納音 30 = **660 種組合**，乘上原有變體。

### 下一個可加的維度

同樣的邏輯還能再往下挖：對方的日干／日支（現在只用了使用者這一方）、時柱的天干地支、雙方生肖的具體配對。每一項都是「已經算出來但沒用」的資訊。

## 敘事改由盤面格局決定，不由分數決定

### 問題

前三段（現在的狀態／卡住的是什麼／值得珍惜的是什麼）原本由分數推出來：分數帶決定第一段，最低／最高維度決定後兩段。

但**分數是加權平均，是衍生數字，不是盤面事實**。實測：

```
「最低維度」與次低的差距
  差 0–2 分 ： 10.9%   ← 這時候說「真正卡住你們的是溫度」是硬掰
  差 3–7 分 ： 23.6%
  差 8 分以上： 65.5%   ← 只有這裡才真的有短板

三項全距 10 分以內：10.0%   ← 根本沒有最高最低可言
```

有三分之一的情況，「最低維度」只是雜訊。

### 解法

`shape.js` 先判讀盤面**配置**，再決定要怎麼說。分數只用來排名與呈現。

十種格局，依合／沖／位置對等三個軸判定：

| 格局 | 條件 | 出現率 |
|---|---|---|
| `onePoint` 單一亮點 | 一合，其餘平 | 22.7% |
| `oneSnag` 單一卡點 | 一沖害，其餘平 | 16.4% |
| `mixed` 一合一沖 | 同時有合與沖 | 16.4% |
| `quiet` 全平 | 兩項皆 ping | 10.9% |
| `doubleClash` 雙沖害 | 兩項皆沖害 | 10.0% |
| `pressed` 沖＋壓 | 一沖害 ＋ 日干相剋 | 9.1% |
| `blank` 空盤 | 全平 ＋ 位置對等 | 4.5% |
| `plain` 平常 | 其餘 | 3.6% |
| `sweetUneven` 合但不對等 | 雙合 ＋ 日干相剋／相生 | 3.6% |
| `harmony` 整齊 | 雙合 ＋ 位置對等 | 2.7% |

### 沒有短板時就說沒有

差距不足 8 分時**不指名短板**，改成誠實的說法：

> 你們三個維度的分數很接近，盤上沒有一個明顯的短板。這代表現在的狀態不是被某件事拖住的，而是整體就停在這個位置。

實測 34.5% 的組合走這條路。這比硬指一個維度更準，也更可信——**敢說「沒有」的判讀才會讓人相信說「有」的時候是真的**。

同理，兩個高分接近且都遠高於最低時，會走「雙強項」的說法，不會因為兩者差距小就說「沒有強項」（這個 bug 在實作時抓到過）。
