# 文案模板資料庫 · 寫作規範

模板資料庫的難處不在「寫得好」，在**三截拼起來之後才會出現的錯誤**。這些錯誤單看陣列全都看不出來，只有窮舉組合才會浮現。

`lint.js` 把「上下語意一致」拆成六條可以機器驗的規則。補新句子之後跑一次：

```bash
node lint.js     # 全部通過會回傳 0，有問題回傳 1
```

---

## 三截各自的職責

```
open   建立語氣，不碰判斷        ← 可省略，且只給最低分維度用
core   下判斷，固定不可變        ← 這是分數的文字化
close  往前推一步：後果／趨勢／做法
```

**判準：把 core 遮起來，open 應該還看不出結論；把 close 遮起來，core 應該還是完整的一句話。**

---

## 六條規則

| | 規則 | 為什麼 |
|---|---|---|
| R1 | 開場句不得下判斷 | open 先講了結論，core 就變成重述 |
| R2 | 開場句與 core 不得語意重述 | 這是「答案不在盤上／沒有先天長度／沒有註定」三句同義的成因 |
| R3 | close 不得重述 core | close 要往前推，不是換句話說再講一次 |
| R4 | 一段之內最多一個未來預測 | 免費層給趨勢不給事件；兩個預測會讓時間軸失焦 |
| R5 | 語氣極性不得衝突 | 「先講好消息」接負面判斷，讀起來像兩個人寫的 |
| R6 | 字面重複（6 字以上） | 最基本的一條，但只能抓字面 |

### R2／R3 靠概念群，不靠字面

字面比對抓不到「換句話說」。`CONCEPTS` 把字面不同但講同一件事的詞歸成同一群：

```js
命定: ['註定','命定','先天','天生','本來就','不在盤上','底子','既定']
未來: ['接下來','往後','之後','近期','會出現','會有一次','將會']
消耗: ['消耗','磨掉','磨損','耗力','損耗','累積','疲勞']
位置: ['位置','話語權','退讓','配合的那個','主導','定調','不對等']
```

open 與 core 只要共用一個概念群就擋下來。core 與 close 允許延續（同一主題本來就會接續），但共用三群以上會被擋。

**補新文案時如果出現新的概念，記得把同義詞加進 `CONCEPTS`**，否則那一群的重複就檢查不到。

### R5 要處理否定

「小摩擦**不會累積**成問題」含「累積」但意思是正面的。規則先移除被否定的子句再判斷極性：

```js
const body = (core + close).replace(/(不會|不再|沒有|不容易|不至於)[^，。；]{0,10}/g, '');
```

---

## 這套規則抓到過什麼

第一次跑就抓到 4 類真的問題（207 個組合）：

- 重量 `b_sheng_a` 的開場「有些付出安靜到不容易被察覺」與 core「主要在給的人是對方」共用「給予」概念
- 長度 `sanhe` 的開場「往後幾年會證明這件事」與 core「往後幾年你們的人生節點會對得上」語意與字面雙重重複
- 重量 `a_sheng_b`／長度 `xing` 的開場語氣與內文極性相反

另外校準了兩處誤判：「舒服」在本產品常指**對方舒服＝使用者累**，不算正面訊號；否定句要先剝掉再判極性。

---

## 結構上的兩個保險

除了規則檢查，還有兩個設計層面的保險：

**一、開場句只給分數最低的維度用。** 三個維度都帶開場句，連讀就是公式。實測 67.4% 的報告有一段帶開場句，沒有任何一份會出現兩段以上。

**二、core 永遠固定。** 判斷句不做變體。變體只出現在 open 與 close，所以再怎麼組合，分數對應的判斷永遠一致——這是「語意邏輯一致」最根本的保障。

---

## 補文案的流程

1. 往 `open` / `close` 陣列加句子
2. 新概念記得加進 `CONCEPTS`
3. `node lint.js` —— 必須全過
4. **抽三到五組完整輸出實際讀過** —— 規則檢查不能取代人眼，語意是否通順只有讀才知道

第 4 步不能省。這次的重複問題就是只跑了自動檢查、沒讀輸出才漏掉的。
